Architecture review · deepening opportunities

intEHRgrator seams for openEHR-as-source & dual builds

Friction surfaced with an eye on merging kintegrate-style openEHR source handling and shipping separate web app and VS Code / Cursor builds. Vocabulary: module, interface, implementation, depth, seam, adapter, leverage, locality (architecture skill); domain terms from CONTEXT.md.

1. Source Format Handler seam

Files: src/core/source/*, src/types/mod.ts, src/core/expression/mod.ts, src/core/codegen/mod.ts, src/workbench/controller.ts

Done

Problem

Source handling is a closed "json" | "xml" union threaded through types, query runtime, codegen, and the workbench. openEHR Composition / FLAT / STRUCTURED as a Source Schema (kintegrate Integration Builder treats openEHR JSON as input) cannot plug in without forking four modules. Deletion test: deleting query_runtime does not vanish complexity — it reappears in every caller — but the format switch itself is shallow branching, not a deep format module.

Solution

Deepen a Source Format Handler module: one small interface (loadSchema, loadInstance, toTree, pathToExpression, createContext, evaluate) with adapters for JSON, XML, and later openehr-composition (and OPT-as-source tree if needed). Mapping Expressions stay format-backed behind that seam; Target Template Skeleton / ehrtslib remain the openEHR target stack.

Benefits

  • Leverage: callers (Click-to-Map, Test Run, codegen) keep one path language insertion API while formats multiply.
  • Locality: openEHR path / FLAT quirks live in one adapter, not scattered unions.
  • Tests: each adapter tested at the Source Format Handler interface; workbench tests stay format-agnostic.

2. Host Abstraction + dual build entries

Files: src/host/web_adapter.ts, src/core/persistence/mod.ts, web/main.ts, scripts/build.ts, ui/split_pane.ts

Done

Problem

Host Abstraction exists but is browser-shaped (File), co-located with WebHostAdapter, and storage is inverted: IndexedDB helpers live in core/persistence while the host re-exports them. Only one esbuild entry (web/main.ts). A VS Code / Cursor webview build cannot swap storage/FS without dragging IndexedDB or forking persistence. One adapter today ⇒ seam still partly hypothetical.

Solution

Deepen Host: bytes/text pick API (no DOM File); move IndexedDB behind WebHostAdapter; keep Project Bundle serialize/import as a deep pure module. Add second build entry (extension/ host + webview bundle sharing Mapping Editor). Prefer webview = same DOM stack; only Host + packaging differ — same pattern kintegrate is moving toward for Codespaces.

Benefits

  • Leverage: one workbench + Blockly stack; two thin host adapters.
  • Locality: storage/FS/AI differences stop leaking into Mapping Model and Test Run.
  • Tests: Host mocked in unit tests (already starting); UI tests reuse Workbench Test API inside either shell.

3. Prefer Blockly JSON over a custom Mapping Spec DSL

Files: docs/MAPPING_SPECIFICATION.md, src/core/mapping_model, ProjectBundle.mapping.blocklyState, AI suggestion format · ADR 0001

Done

Problem

Sync Scope today invents a third language: Blockly blocks ⇄ Mapping Model ⇄ custom block-aligned DSL (toSpec / @template composition { … }). That DSL is not known to LLMs, not used by other tools, and duplicates structure already in Blockly.serialization.workspaces.save (persisted as blocklyState). Deletion test: removing core/spec mostly removes projection chrome — Mapping Model + Blockly JSON already carry the mapping. Growing the DSL toward text-first editing doubles maintenance without industry familiarity.

Solution

Treat Blockly native JSON as the canonical Mapping Specification / interchange surface (DeepWiki: RaspberryPiFoundation/blockly serialization — documented blocks / fields / inputs / extraState contract; intended for restore and interchange). Keep the slim Mapping Model (slotId → expression) as a derived index for AI patch import (intehrgrator-suggestions), validation, and Test Run — not a parallel structural language. Center CodeMirror should show pretty-printed Blockly JSON (optionally stripped of x/y for readability) or the Mapping Model slot list — not a hand-rolled DSL. Informatician expression edits either patch Blockly field JSON paths or the derived slots[]; structural edits stay in Blockly / Optional RM Insertion.

Benefits

  • Leverage: LLMs and tooling already see Blockly serialization in the wild; no need to teach a private DSL.
  • Locality: one structural truth (blocklyState); Mapping Model regenerates from it; toSpec can shrink or die.
  • AI path: bulk structure via Blockly JSON; slot fills via existing small suggestion envelope — best of both.
Caveat: raw workspace JSON includes UI chrome (coordinates, shadows, ids). Persist the full form; for human/LLM review prefer a filtered projection (drop x/y, maybe collapse fixed RM shells) or the Mapping Model slot table — still JSON, still not a new grammar. Blockly major bumps can change serialization; pin Blockly and keep Mapping Model as the migration-friendly index.
Before — three languages
custom DSL ⇄ Mapping Model ⇄ Blockly JSON
toSpec projection · expression line parser · AI learns private @template syntax · dual persistence confusion
After — Blockly JSON + derived index
blocklyState (canonical) → Mapping Model slots[] (derived)
CodeMirror: Blockly JSON or slots JSON · AI: suggestions envelope and/or Blockly JSON patches · codegen/Test Run from Model

4. Mapping pipeline depth (Sync Scope → Test Run)

Files: src/blockly/*, src/core/mapping_model, src/core/codegen, src/core/test_runner, web/main.ts

Done

Problem

Intended Sync Scope is Blockly ⇄ Mapping Model (⇄ text projection) → Generated Export → Test Run. Actual path: Click-to-Map updates Mapping Model; Blockly canvas edits only markDirty(); Test Run evaluates slot expressions into a stub Composition and ignores Generated Export. Dual codegen (Blockly JS generators vs core/codegen) splits locality. UI tests can assert slot preview today, but not “sensible openEHR Composition” until this deepens. Pair with candidate 3: do not deepen a custom DSL while fixing the pipeline.

Solution

Make Blockly JSON → Mapping Model the sync authority: Blockly → Model on change; codegen only from Model; Test Run executes Generated Export (or a Model interpreter that is the same semantic surface). Collapse or demote unused Blockly-only generator path until it is an adapter behind the same interface. Demote or delete toSpec DSL as the center-pane “language.”

Benefits

  • Locality: bugs in conversion live in one pipeline, not Model vs Blockly vs stub runner.
  • Leverage: Workbench Test API / UI tests assert real Composition JSON.
  • Deletion test: today’s thin test_runner fails — deleting it barely hurts; after deepening, deleting it would force N callers to reimplement ehrtslib execution.
Before
runTest(model, example)
evaluate each slot → { COMPOSITION stub, slots } · _generatedTs unused
After
runTest(model | generatedExport, example) → Composition
Sync Scope guarantees Model freshness · ehrtslib build · validation warnings with locality next to codegen

5. Collapse pass-through RM attachment catalog

Files: src/core/rm_attachment_catalog.ts, src/core/rm_meta.ts

Worth exploring

Problem

rm_attachment_catalog.ts is a ~10-line re-export of getValidAttachments. Deletion test: complexity vanishes — it was a pass-through. Optional RM Insertion policy (what to offer in the picker) belongs either inside a deepened attachment module or directly on rm_meta.

Solution

Either delete the catalog and import rm_meta, or deepen it into the real Optional RM Insertion policy module (OPT context, already-present attrs, product filters) — that would earn depth once openEHR-as-source and dual hosts need consistent attachment rules.

Benefits

Less AI-navigation noise; or, if deepened, one locality for attachment policy tests.

After (pick one)

6. Workbench view seam (shell vs controller)

Files: web/main.ts, src/workbench/controller.ts, tree_views.ts, codemirror_setup.ts

Worth exploring

Problem

WorkbenchController is mostly host-agnostic and deep, but web/main.ts owns dialogs, Blockly inject, and render wiring (~500+ LOC). Fine for one web app; painful when a second shell (VS Code webview HTML) must fork that glue. Workbench Test API already peeks through this seam — a good sign the interface wants formalizing.

Solution

Extract a thin Workbench Shell module that mounts Mapping Editor + Source Pane + Output Previews given a Host + DOM roots. Web Pages and VS Code webview become two adapters that only supply roots + Host. Keep Workbench Test API as the test surface of that shell.

Benefits

Locality for UI wiring; leverage for dual builds without duplicating Click-to-Map / Autoplay glue.

Do this after or alongside Host deepening — extracting a shell that still hard-codes File / IndexedDB only moves the shallow edge.

7. Handlebars / kintegrate conversion dialect

See docs/KINTEGRATE_MIGRATION.md, Target instance format handlers, Better Form Bridge

In progress

Problem

kintegrate’s middle column is Handlebars conversion scripts over JSON trees (often openEHR compositions). intEHRgrator’s Conversion script language is TypeScript/Java from Blockly. Merging product surfaces may tempt a third script language without a deep Conversion script language module.

Solution

Only if product requires it: deepen Conversion script language as adapters behind Mapping Model (typescript | java | handlebars), never a parallel IR. Prefer absorbing kintegrate’s source strengths first (candidate 1).

Benefits

Avoids a second mapping language; keeps AI / Blockly / spec on one Model.

Top recommendation
