Problem. Three registries decide which languages exist (the codegen map, Blockly overrides that depend on call order, and #332's plugin map with its global generator). Every caller branches on which one applies.

Solution. One module owns every language, built-ins included, as plugins behind one interface. The plugin loader is its adapter.

  • locality: one place adds a language
  • leverage: 4 callers, 1 interface
  • Blockly init order stops mattering
  • VMS golden tests cross the same seam
  • two adapters make it a real seam

Conversion input
interface: one serializable value · implementation: encoding rules, Blockly JSON, skeleton

Problem. Script options (instance shape, skeleton, Blockly state, Web Template) are built in 6 places on main and 8 with the PRs. The TypeScript and Go walkers need a live Blockly Workspace, which can't be passed to a worker.

Solution. One function turns workbench state or a file project into a serializable Conversion input. The walkers read Blockly JSON.

  • interface shrinks to one value
  • locality: encoding rules in one place
  • plugins become worker-safe
  • file project matches the workbench

Problem. In #332 the agent depends on the desktop, the Web adapter carries a desktop-only method that Pages also gets, and web/main.ts calls the agent API itself.

Solution. Each host only serves plugin bytes from its same-origin plugins/ folder. Execution always happens in the registry's worker adapter.

  • agent → desktop import gone
  • 4 adapters, 2 small methods
  • no desktop-only optional method
  • same behaviour in every release format

Problem. The desktop UI runs the Web adapter and detects the desktop through page globals. Six modules call /api/v1 themselves.

Solution. createHostAdapter returns a desktop adapter that owns the token, the backend calls and the AI proxy.

  • globals stop leaking into UI
  • locality: backend calls in one adapter
  • desktop testable with a fake adapter

Problem. Four bundle-store methods on HostAdapter assume a Project Bundle. VS Code file projects bypass them through the concrete adapter and switch off autosave and undo.

Solution. One store interface that also says who owns undo, with the four stores as adapters.

  • file projects stop bypassing the seam
  • undo ownership in the interface
  • headless and UI open projects alike
⚠ Touches ADR 0014 (one history) and #305's decision that VS Code owns undo in file projects. Only worth reopening if a fourth store appears.

Top recommendation

One registry and one Conversion input, as the first slice of #336

Every language, our own included, goes through one interface and one worker seam. 3 registries become one and 8 option-building sites become one function, and the VMS golden tests cross the same seam that users do.

Which of these would you like to explore?

  1. Port the TS and Go walkers to Blockly JSON, or bundle headless Blockly into those plugins?
  2. Should the desktop UI generate in a browser worker like web and VS Code, with the Deno worker only for headless, MCP and --check?
  3. A ProjectStore now (touches ADR 0014 and #305), or only when a fourth store appears?
  4. Echo in the release plugins/index.json, or dev builds only?
